# ChronosLock — конкурентное бронирование временных ресурсов в Go и PostgreSQL

Практический пример высококонкурентного сервиса бронирования ресурсов с временными диапазонами.

Проект показывает, как построить систему, в которой **несколько экземпляров Go-сервиса в Kubernetes одновременно получают запросы на один ресурс, но база данных гарантирует отсутствие пересекающихся бронирований**.

В основе решения — PostgreSQL `TSRANGE`, GiST, `EXCLUDE CONSTRAINT`, `SELECT FOR UPDATE`, транзакции и локальные блокировки Go.

## 💡 Какую проблему решает проект

Представим, что несколько пользователей одновременно пытаются забронировать одну переговорную комнату на один и тот же промежуток:

```text
Пользователь A ──────── 10:00 ───────── 12:00
Пользователь B ──────── 10:00 ───────── 12:00
Пользователь C ──────── 10:00 ───────── 12:00
```

Если проверять доступность ресурса только в Go:

```sql
SELECT ...
```

а затем отдельно выполнять:

```sql
INSERT ...
```

между этими операциями возникает окно Race Condition.

Несколько экземпляров сервиса могут одновременно решить:

> «Ресурс свободен, можно создавать бронирование».

В результате система может записать конфликтующие диапазоны.

ChronosLock переносит критически важную гарантию на уровень PostgreSQL.

```text
                 Kubernetes
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   Go Pod #1    Go Pod #2    Go Pod #3
       │            │            │
       └────────────┼────────────┘
                    ▼
              PostgreSQL
                    │
          EXCLUDE USING GiST
                    │
                    ▼
       Пересекающиеся диапазоны
             отклоняются
```

Даже если несколько pod одновременно попытаются создать конфликтующее бронирование, PostgreSQL не позволит нарушить ограничение.

# 🔐 Основная идея

Проект демонстрирует многоуровневую защиту конкурентных операций.

### 1. PostgreSQL `TSRANGE`

Временной интервал хранится непосредственно как диапазон PostgreSQL:

```sql
booking_period TSRANGE NOT NULL
```

Это позволяет базе данных работать со временем как с диапазоном, а не как с двумя несвязанными значениями `start` и `end`.

---

### 2. GiST + `EXCLUDE CONSTRAINT`

Главная гарантия отсутствия пересечений реализована на уровне PostgreSQL:

```sql
CONSTRAINT no_overlapping_reservations
EXCLUDE USING gist (
    resource_id WITH =,
    booking_period WITH &&
)
```

Логика ограничения:

> Для одного ресурса два временных диапазона не могут пересекаться.

Это важнее обычной проверки в Go, потому что правило защищено самой базой данных.

Даже если появится второй экземпляр приложения, дополнительный сервис или другой клиент, который напрямую пишет в PostgreSQL, ограничение продолжает действовать.

---

### 3. `SELECT FOR UPDATE`

Для конкурентной работы нескольких pod используется пессимистическая блокировка:

```sql
SELECT ...
FOR UPDATE
```

Она позволяет сериализовать критические операции над одной записью.

Это особенно полезно при работе нескольких экземпляров приложения:

```text
Pod #1 ──┐
         │
Pod #2 ──┼──> PostgreSQL ──> блокировка ресурса
         │
Pod #3 ──┘
```

---

### 4. Локальная блокировка внутри pod

В приложении используется `sync.Map` для организации сегментированных блокировок.

Это позволяет отсеивать часть конкурирующих запросов ещё до обращения к PostgreSQL.

Получается двухуровневая схема:

```text
Go pod
  │
  ├── In-memory lock
  │
  ▼
PostgreSQL
  │
  ├── Transaction
  ├── SELECT FOR UPDATE
  └── EXCLUDE USING GiST
```

Локальная блокировка не заменяет защиту PostgreSQL.

Она является оптимизацией для конкурирующих запросов, приходящих в один экземпляр приложения.

---

## 🛡️ Почему защита находится на нескольких уровнях

Каждый механизм решает свою задачу.

| Механизм             | Задача                                                |
| -------------------- | ----------------------------------------------------- |
| Go validation        | Отсекает некорректные даты до обращения к БД          |
| `sync.Map`           | Снижает локальную конкуренцию внутри pod              |
| `SELECT FOR UPDATE`  | Синхронизирует конкурентные операции через PostgreSQL |
| `EXCLUDE USING GiST` | Физически запрещает пересекающиеся бронирования       |
| Context timeout      | Не позволяет запросам зависать бесконечно             |
| Graceful shutdown    | Позволяет корректно завершить активные операции       |
| UTC normalization    | Устраняет проблемы с часовыми поясами                 |

Такой подход показывает важный принцип:

> Критическая целостность данных не должна зависеть только от корректности кода приложения.

# 🧪 Проверка Race Conditions

После запуска трёх реплик можно отправить несколько конкурентных запросов:

```bash
for i in {1..10}; do
    curl -i http://localhost:8080/book &
done
wait
```

Все запросы пытаются забронировать один и тот же ресурс.

Ожидаемое поведение:

```text
1 запрос  → 201 Created
9 запросов → 409 Conflict
```

При этом в PostgreSQL должна остаться только одна конфликтующая запись.

Проверка:

```bash
kubectl exec -it <ИМЯ_ПОДА_POSTGRES> -- \
psql -U user -d booking_db \
-c "SELECT * FROM reservations;"
```

Это позволяет не просто посмотреть код, а **самостоятельно воспроизвести конкурентную ситуацию и проверить результат**.

# 📊 Проверка индекса через EXPLAIN ANALYZE

Проект также показывает, как исследовать фактический план выполнения PostgreSQL.

Например:

```sql
EXPLAIN ANALYZE
SELECT id
FROM reservations
WHERE booking_period &&
      tsrange(
          '2026-07-01 00:00:00',
          '2026-07-01 02:00:00'
      );
```

В плане можно увидеть:

```text
Bitmap Heap Scan
    └── Bitmap Index Scan
```

Это позволяет проверить, как PostgreSQL использует индекс для поиска диапазонов.

Важно: `Bitmap Index Scan` не является гарантированным результатом для любого объёма данных или любого запроса. План выбирается оптимизатором PostgreSQL исходя из статистики, стоимости операций и текущего состояния таблицы.

Поэтому проект можно использовать как практический стенд для экспериментов с:

* количеством записей;
* статистикой PostgreSQL;
* разными типами запросов;
* индексами;
* селективностью условий;
* планами выполнения.

Подключитесь к PostgreSQL:

```bash
kubectl get pods -l app=postgres
```

Затем:

```bash
kubectl exec -it <ИМЯ_ПОДА_POSTGRES> -- \
psql -U user -d booking_db
```

Создайте расширение и таблицы:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE resources (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(255) NOT NULL
);

CREATE TABLE reservations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    resource_id UUID NOT NULL
        REFERENCES resources(id)
        ON DELETE CASCADE,

    booking_period TSRANGE NOT NULL,

    created_at TIMESTAMP WITH TIME ZONE
        DEFAULT NOW(),

    CONSTRAINT no_overlapping_reservations
    EXCLUDE USING gist (
        resource_id WITH =,
        booking_period WITH &&
    )
);
```
